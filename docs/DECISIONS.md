# 已确认规则

以下规则为当前项目基线，后续修改必须记录原因、日期和影响。

## 项目与运行环境

- 本项目为全新独立项目，与其他交易系统无关；
- 开发目标环境为macOS，部署目标环境为Linux服务器；
- 统一使用Node.js 24、TypeScript和UTC时间；
- 同一套策略逻辑同时服务PAPER和LIVE，差异仅位于执行适配器；
- 同一时刻只允许一个实盘实例拥有下单权。

## 市场范围

- 第一版只处理结果明确且结果数为2或3的事件；
- 普通YES/NO市场视为2个结果；
- 排除结果数超过3、含义不清、动态Other或未命名占位结果的事件；
- 体育市场在比赛开始后停止新买和重新挂买，已有持仓及卖单继续处理；
- 程序不维护地域限制名单，也不主动按地域阻断；若Polymarket拒绝实盘订单，记录错误并停止新订单，不重复尝试，不规避平台限制。

## 交易规则

- 买价范围为0.01至0.03；
- 单笔预算为1U；
- 使用Maker挂单，不主动吃单；
- 同一Token在每轮策略运行中只允许一个完整交易周期；
- 出现第一笔卖出成交后，撤销该Token剩余买单，并永久停止该轮新买，直至人工重置；
- 第一版不扩大到3个以上结果的事件。

## PAPER成交规则

- PAPER和LIVE读取相同的公开市场、盘口和成交数据；
- PAPER订单不进入真实队列，因此成交必须模拟；
- 下单时记录可见的前方排队量；
- 只有下单后同价位累计成交量超过前方排队量的部分，才能计入纸面成交；
- 不把前方撤单计为有利成交；
- 断线、数据缺失或顺序不确定时不确认成交。

## 实盘边界

- 当前版本实盘执行器必须保持禁用；
- 纸面闭环和长时间验证完成前不得接入钱包；
- 钱包密钥不得进入代码、数据库、Git、日志、Issue或聊天；
- 实盘订单被平台拒绝后停止新订单并等待人工处理。

## UI、Linux部署与长期验证顺序（2026-08-05）

- 原因：正式长期验证需要同时覆盖最终操作界面和服务器部署状态，不能只在本机命令行完成后再补验UI与部署。
- 执行顺序固定为：确认并实现最终TEST UI（内部执行模式仍为`PAPER`）；以`PAPER + LIVE_DISABLED`部署到Linux服务器并完成短时冒烟；由用户制定正式长期验证的时长、故障场景和验收门槛；最后在该部署上开始长期验证。
- UI和Linux冒烟只验证接线、展示、控制、重启恢复与安全边界，不计入正式长期运行时长；用户确认计划前仍不得自行启动长时间运行。
- 这一顺序不构成钱包或实盘授权。纸面闭环和正式长期验证全部完成前，钱包、签名、真实订单及链上写操作继续保持禁用。

## Linux TEST跨设备访问边界（2026-08-05）

- 原因：用户需要离开电脑后仍可直接从手机查看和控制TEST，同时不能把无内置认证的控制及配置接口裸露到公网。
- 当前Linux TEST部署使用固定公网IPv4的受信任HTTPS链接和Nginx登录认证；手机与电脑均可直接使用浏览器，不要求安装私网客户端。
- Docker应用端口必须只绑定`127.0.0.1`；云防火墙只为网页保留TCP 80/443，不得放行应用3000端口。80仅用于ACME验证及跳转，实际页面和API全部走443认证代理。
- 登录凭据及哈希不得进入Git；反向代理不得把`Authorization`头传给应用，并拒绝浏览器明确标记为跨站的请求。证书续期必须全自动并在续期后先校验再重载Nginx。
- 该入口只服务当前`PAPER + LIVE_DISABLED`部署，不构成账户系统、钱包或LIVE授权。若未来进入LIVE设计，必须重新评估强身份认证、会话、CSRF、审计和密钥边界。

## 最终UI信息层级（2026-08-05）

- 视觉方向已确认并落地：使用Vercel式轻量骨架、Coinbase式财务数字表达和Binance式紧凑市场行密度，保留PM-SMALL青绿色；不复制品牌配色、营销留白、横向滚动表格或实盘紧迫感。
- 主界面以手机使用为优先，同时自然适配桌面；至少支持320px宽度，不依赖横向表格完成主要操作。
- 左上角只显示可点击的`TEST / LIVE`模式入口；`TEST`只是界面名称，内部执行模式、数据库和安全语义继续使用`PAPER`。长期验证和钱包授权完成前，点击`LIVE`只提示尚未开放，不能改变实际执行模式。
- 默认主界面只保留资金盈亏、当前持仓和扫描市场；桌面和手机均按单列竖向排列，不使用双栏；不显示筛选说明、最近活动、程序状态、服务器状态、连接诊断或验证细节。
- 配置按需展开，只提供二元/三元市场多选、最高买入价格和市场总时长。二元与三元可同时选择；最高买入价格只能使用`1¢`、`2¢`或`3¢`整数值，默认`≤3¢`；开放、允许下单、具有订单簿等固定资格条件不在界面重复展示。
- 资金盈亏展示总资金、总盈亏、已实现和未实现。每个持仓展示可点击的市场名称、结果方向、加权平均买入价，以及从市场开始到结束的总时长进度；买入的结果方向使用醒目的独立标签。
- 扫描市场提供总时长进度“正序/倒序”切换，默认正序；每项展示可点击的市场名称、结果方向、策略买入价和总时长进度。
- 合格扫描结果默认全部勾选并进入TEST自动交易范围，取消勾选即排除；提供全选和清空。首屏显示20项，每次再显示20项。
- 二元/三元、最高买入价和总时长设置持久化到SQLite并作用于后续完整扫描；改变总时长时仍遍历对应安全窗口内全部分页，不引入市场数量上限。保存后即使旧扫描快照尚未替换，新设置也会立即过滤候选响应，并在自动及手动PAPER买入入口再次校验，避免时间窗口内继续建立已被排除的新买单。
- 市场选择按Token结果方向持久化。取消单项或清空会阻止对应Token继续自动买入，并撤销其尚未成交的PAPER买单；已有持仓和减仓卖单继续保留，避免把范围选择误当作强制平仓。单项选择只接受当前扫描中仍符合过滤条件的Token，拒绝陈旧或任意Token写入。
- 总资金按可用资金、挂单占用和全部正数量当前持仓估值合计，不以界面分页或固定行数截断；未实现盈亏优先使用完整盘口最佳买价估值，缺失时依次回退到候选价格和持仓成本。回退只用于展示，不放宽成交确认规则。
- 配置文件或SQLite中的最高价格、结果数量或总时长若超出上述离散范围，进程应在启动时失败并要求人工修正，不能静默夹取或让界面显示与运行值不一致。
- Linux部署时，控制及配置接口必须通过反向代理认证或受限网络边界保护；本轮不引入账户、钱包或任何LIVE凭据。

## TEST运行控制与新一轮规则（2026-08-05）

- 顶部提供明确的`开始TEST / 暂停TEST`控制。普通开始只从当前SQLite账本继续运行，不清空持仓、活动卖单、资金或历史盈亏，也不解除已发生首次卖出的Token周期锁；暂停会撤销活动买单的未成交部分，持仓和卖单继续保留。
- 保存二元/三元、最高买入价或总时长时，必须在同一SQLite事务内更新配置并撤销因任一新条件不再合格的活动PAPER买单；部分成交形成的持仓及对应卖单继续保留。若账本安全闩阻止撤单，配置保存也必须整体失败，不能只写入一半状态。
- `开始新一轮`是同一Token重新参与买入的唯一人工入口，且只能在`PAUSED`或`STOPPED`时执行。它先通过账本一致性验证，只解除数量和成本均为0、已完整卖出且尚未正式结算的Token周期锁，然后进入`RUNNING`。
- 新一轮不得清空或改写未完成持仓、活动卖单、可用及占用资金、已实现/未实现计算基础或历史审计；已正式结算的Condition永久不得解锁。其他未被周期锁定的合格市场始终可以使用已释放资金继续自动交易，不需要等待新一轮。

## v0.4.0正式结算规则（2026-08-03）

- 原因：完成纸面闭环，同时避免把市场关闭或临时价格变化误当作正式结果。
- 影响：只有市场`closed=true`且正式结算状态为`resolved`或`settled`时才处理；结果价格必须是二元`1/0`或官方`0.5/0.5`向量，其他状态继续等待。
- 纸面模式不调用钱包、签名、赎回或链上接口；获胜Token回收按正式结果模拟，失败Token归零。
- 使用Condition ID作为一次性结算键；重复结果不重复记账，身份冲突或数据不一致时暂停策略并保留审计记录。

## 全市场分页扫描规则（2026-08-04）

- 原因：用户要求扫描 Polymarket 全部市场，不能因为数据源第一页或本地 Token 数量上限漏掉候选。
- 影响：开放事件使用官方分页迭代器遍历全部页面；不再截断候选 Token 数量，订单簿请求仍按平台批量大小分批读取。
- 为避免先下载逻辑上不可能合格的事件，扫描按当前时间和所选总时长构造安全窗口：开始时间位于`now-maxDuration`至`now`，结束时间位于`now`至`now+maxDuration`；任何当前已开始、未结束且总时长不超过上限的事件必然落在该窗口内。窗口内仍遍历全部分页，精确总时长、进度和市场资格继续在本地复核。
- 市场资格仍需同时满足：事件开放且未关闭/归档，底层市场 active、未关闭、允许下单并启用订单簿，且具备 Condition ID；订单簿和价格规则继续由现有 PAPER 策略校验。
- `MAX_MARKET_DURATION_DAYS` 是筛选参数，默认 30 天；它只决定市场总时长上限，不限制扫描页数或市场总量。
- 最终 UI 使用已接入运行配置的离散滑杆调整该上限，节点固定为 `1、7、14、30、60、90、120、180、360、365` 天，默认停在 30 天。

## v0.5.0全市场只读请求恢复规则（2026-08-05）

- 原因：默认30天完整扫描已达到数分钟，单个暂时接口错误不应丢弃此前已读取的全部事件页或订单簿批次；同时不能用无限重试掩盖持续故障。
- Polymarket当前官方文档要求对`429`和`500`采用指数退避，并说明匹配引擎重启时`425`属于暂时状态；接口限额与平台行为以后续长期运行时的[Rate Limits](https://docs.polymarket.com/api-reference/rate-limits)、[Error Codes](https://docs.polymarket.com/resources/error-codes)和[Matching Engine Restarts](https://docs.polymarket.com/trading/matching-engine)为核对基线。
- 每个事件分页游标和每个50 Token订单簿批次最多请求3次，失败后分别等待1秒、2秒；重试只重复当前游标或当前批次，不重新开始已完成的扫描，也不增加本地页数、市场数或Token数上限。
- 只重试SDK限流错误、传输错误、异常响应，以及HTTP `408`、`425`和`5xx`；`400`、`404`等永久性客户端错误立即失败。取消信号在请求等待和退避等待中均应及时结束本轮扫描。
- 状态诊断分别保留事件页请求数、订单簿请求数、重试数、限流数和临时错误数；长期JSONL样本原样记录，恢复行为产生告警，汇总保留窗口最大值。计数与自动测试通过不代表真实接口长期容量验收完成。
- 该恢复机制只读取公开数据，不接入钱包、签名、真实订单或链上写操作；最终失败仍沿用保留上一批成功候选和暴露`FAILED`诊断的保守规则。

## v0.5.0周期一致性验证规则（2026-08-04）

- 原因：长期 PAPER 运行需要持续发现 SQLite 损坏、资金不守恒、订单成交范围错误、挂单占用错误、持仓卖单覆盖错误和结算残留，不能只依赖启动时的一次恢复核对。
- 周期服务默认每 60 秒执行一次只读验证，最后一次周期结果进入 `/api/status`；`GET /api/paper/validation` 提供独立的即时只读检查，不改写策略状态或审计。
- 周期服务发现验证失败时直接将策略置为 `PAUSED` 并记录审计，不依据不一致账本自动撤单、结算或改账；只有卖单可继续减仓。即使暂停状态无法写入SQLite，进程内安全闩也必须执行同样的冻结边界。
- 账本未恢复通过前禁止重新进入 `RUNNING`；恢复时先撤销冻结期间已发生首次卖出的Token遗留买单，继续遵守单轮永久停买规则。验证能力完成不代表 v0.5.0 长期运行、故障注入或性能验收已经完成。
- 该机制仅服务 PAPER，不引入钱包、签名、真实订单或链上操作。
- 长期运行证据采用只读本机API采样和JSONL追加记录，默认存放于不受Git跟踪的`data/validation/`；模式/LIVE或账本错误立即停止，外部数据源暂时错误先记告警以观察恢复。
- 到达正式长时间PAPER验证阶段后，代理必须停止，不自行决定运行时长、故障场景或验收门槛；由用户先制定验证计划。计划确认前的短时启动/中断检查只算预检，不得计入正式长期验收。
- 留证运行器读取轻量状态，不重复传输候选详情；两个安全接口独立保留已返回结果，任一关键异常都不能被另一接口超时掩盖，零有效样本不得记为成功。
- 为支持未来Linux服务器容量验收，轻量状态和每个JSONL样本记录进程运行时长、RSS、堆总量、堆已用量及外部内存，汇总记录各项窗口最大值。该数据只用于比较运行窗口和确定服务器规格，在正式运行取得基线前不设置武断的自动失败阈值。
- 每次扫描实时记录阶段、事件分页数、事件数、合格Token数、订单簿批次数、订单簿数、候选数和耗时；一次监测正常结束不自动代表v0.5.0验收完成。
- 候选扫描暂时失败时不得用空数组覆盖上一批成功候选；状态必须保留最近成功结果并暴露`lastError`和`FAILED`诊断，下一次成功扫描再原子替换候选并清除错误。等待`refresh()`或`GET /api/candidates?refresh=true`完成后返回的是已结束快照，`scanning`必须为`false`。
- 账本故障注入只能在健康数据库的独立副本中执行，不得修改长期证据原件或未来服务器生产库。验证失败后不得绕过暂停门槛；先保留副本和错误证据，核对活动订单占用及资金守恒，再人工修复，最后以即时校验、重新启动和同库冷启动三步确认恢复。
- 2026-08-05的隔离演练将100张活动买单对应的99,990,000微单位保留资金改为0；周期服务自动暂停，即时校验返回503，启动请求返回409。恢复正确占用后，同库冷启动的15个样本均无关键错误或失败校验，并恢复100/100活动订单盘口。该结果只完成账本不一致场景，不代表整个v0.5.0验收完成。

## v0.5.0公开行情快照与有界关停规则（2026-08-04）

- 原因：真实冒烟中，2,452个Token的公开WebSocket已经连接并持续收到增量事件，但完整盘口数保持为0；同时扫描或大订阅进行中常规关停不能及时退出。
- 官方已取消Market频道原100 Token限制，因此不得用固定订阅上限掩盖全市场筛选结果。实测836个Token在订阅帧省略`initial_dump`时只收到增量事件；显式设置`initial_dump: true`后约3秒取得全部初始盘口。
- 公开行情适配层直接发送带`initial_dump: true`的官方订阅帧，并继续发送10秒心跳；只解析公开的`book`、`price_change`和`last_trade_price`，不增加认证、钱包或写操作。
- 停止服务时取消候选扫描，分页和订单簿等待接受`AbortSignal`；WebSocket关闭和重连等待有局部超时，进程收到`SIGINT`或`SIGTERM`后还有5秒总截止线。正常清理退出码为0，清理失败或超时退出码为1。
