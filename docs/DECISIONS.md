# 已确认决策

本文件记录当前有效规则。历史方案、旧交接记录或代码注释与本文件冲突时，以 GitHub `main` 上的本文件为准。

## 安全与阶段边界

- 当前公开模式名为 `TEST`，初始状态为 `PAUSED`；内部 SQLite 表名和审计事件中的 `paper`/`PAPER`属于兼容实现，不是可启用的第二种模式。
- `LIVE` 执行器必须失败关闭。纸面闭环和用户制定的正式长期验证全部完成前，不接钱包、不签名、不发送真实订单、不执行链上写操作。
- TEST 与未来 LIVE 共用市场发现、资格判断、排序、买卖意图、目标价、费用和 FAK 计算；执行结果由适配器隔离。当前只实现 `TestExecutor`，未来 LIVE 仍需单独实现鉴权、下单、撤单、对账、恢复和安全门。
- 自动测试、短时冒烟、部署成功或用户点击 LIVE 都不构成实盘授权。

## 市场遍历与资格

- 用户要求遍历 Polymarket 全部符合条件的市场。扫描必须遍历官方开放事件的全部分页，不设置事件、市场或 Token 数量上限。
- 开放事件按页流式处理，不在内存中保留完整嵌套事件图。先应用不依赖盘口的结果数、类别、总时长、生命周期进度和体育开赛规则，再只为这部分 Token 获取订单簿；盘口请求可以有界并发和分片，但不得用隐藏数量上限截断。
- 不使用事件级开始/结束日期窗口预先截断，因为事件和其具体市场的时间可能不同；精确规则在每个具体市场上执行。
- 事件必须明确 `active=true`、`closed=false`、`archived=false`。具体市场也必须明确 active、未 closed/archived、`acceptingOrders=true`、`enableOrderBook=true`，并具有 Condition ID；缺失布尔状态不得推定为开放。
- 具体市场总时长定义为 `endsAt - openedAt`。优先读取市场自身 `state.startDate/endDate`，缺失时才回退到所属事件时间。
- 总时长最短值和最长值都由用户按完整天数自由设置，各自范围为 1–365 天，且最短值不得超过最长值；默认代表 `1 天 <= 总时长 <= 30 天`。例如设置 7–30 天时，只接受总时长不少于 7 天且不超过 30 天的市场。
- “剩余时间”不参与总时长筛选。市场仍须已经开始且尚未结束。
- 生命周期进度是硬资格门槛，配置范围 1% 至 100%，默认 `<=20%`；超过阈值立即从扫描清单和新买入中排除。排序仍可在合格市场内按进度正序或倒序。
- 体育市场在比赛开始后立即失去新买资格，未完成的旧买单撤销；已有持仓仍可卖出或等待结算。该规则必须进入统一资格函数，不能只在执行器临时拦截。
- 只处理用户勾选的二元和/或三元事件。类别选择只显示 Polymarket 首页顶栏当前栏目，按官方 Tag ID 动态同步并默认全选；首页栏目变化后下一轮同步自动更新，一个市场可匹配多个 Tag。无官方标签的市场只在“全选”下参与，不制造 `OTHER` 等伪官方 ID。
- 非全选时，保存的栏目 ID 必须与本轮同步到的首页栏目取交集；已经退出首页导航的旧 ID 不得继续进入盘口请求或自动执行。栏目同步暂时失败时使用既有受控回退，不阻塞完整市场遍历。
- 不设历史成交量硬门槛。是否能够交易由当前可执行订单簿深度和最小下单量决定。

## 候选与价格

- 所有同时满足结构条件和当前“无盘口静态条件”的 Token 都进入实时盘口监控，包括当前价格高于上限或暂时无盘口的 Token；这样价格进入范围时可立即成为候选。修改结果数、类别、总时长或生命周期进度后必须立即重扫以更新监控池。
- 候选集合变化时在同一公开 WebSocket 上增量订阅或退订，并对大集合分片发送；不得为了普通扫描差异重建整条连接。真实断线时最后有效报价可以继续展示，但必须标记为重连/未就绪且禁止新买，直到该 Token 收到新的完整盘口。大集合的报价更新必须按 Token 索引定位，完整快照按尚未收到 Book 的 Token 集合判断，不能对每条行情重新遍历全部候选或订阅。
- 当前可买候选必须具有完整新鲜盘口和有效 tick；Best Ask 必须在固定最低 `1¢` 至用户买价上限之间；必须存在有效 Best Bid，且 `Best Bid / Best Ask` 不低于用户比例（1%–100%，默认 50%）；本轮金额按 Best Ask 计算后还须达到平台最小下单量。
- REST 或 WebSocket 盘口中的价格必须严格位于 0 与 1U 之间并可安全转换为整数微单位；REST 盘口还必须同时匹配 Token、Condition ID 和 neg-risk 身份，否则只保留监控对象并标记盘口未就绪。
- 最高买价只能为整数 `1¢`、`2¢`或`3¢`，默认 `≤3¢`；最低买价固定为 1¢，不能以 `Best Ask > 0`替代。
- 扫描结果不提供逐 Token 勾选。所有同时符合类别、结果数量、价格、买卖盘比例、生命周期进度、总时长和盘口条件的候选都自动参与 TEST。
- 合格候选按当前生命周期进度正序或倒序，默认正序；排序只影响处理和展示顺序，不放宽进度硬门槛。

## TEST 买入

- TEST 和未来 LIVE 都以实时可成交 Best Ask 为触发条件，不使用等待成交的 Maker 队列模型。
- 买入采用 FAK：在价格上限内从最低 Ask 向上逐档吃单；允许部分成交，未成交余量立即取消。
- FAK 买单按现金上限定义：现金完整使用时订单记为 `FILLED`，其原始份额和已成交份额都等于实际总成交份额；因深度不足只成交部分时订单记为 `CANCELLED`，不得用首档价格估算份额破坏账本不变量。
- 已消耗盘口深度按 BID/ASK 单侧完整盘口状态的稳定版本持久化。重复增量、等价快照、断线重连或进程重启都不得重新释放同一深度；只有该侧实际盘口状态改变后才形成新版本。
- 每个 Token 每轮使用独立现金上限，默认 1U；总 TEST 资金默认 100U。新 Token 或新周期只有可用现金至少等于完整配置金额时才开启；已有部分周期可按剩余额度和当前可用现金继续买入，累计不得超上限。
- 行情、筛选或订单簿不完整时不推定成交。保存配置后，自动入口和诊断用手动 API 都必须立即复核当前配置。
- 行情触发的自动评估只处理本批发生变化的 Token；定时全量校正仍可处理完整候选集合。不得因单 Token 报价变化重新筛选和排序整个监控池。

## 目标卖出与循环

- 每个实际买入填充都立即创建目标卖单，目标为 `max(买价 + 1¢, 买价 × 1.5)`，再按该市场 tick 向上取整。
- Best Bid 达到或高于目标价时立即按 FAK 卖出，从最高可成交 Bid 向下消耗；允许部分成交，剩余数量继续等待同一目标，不主动降价，不设止损。
- 同一 Token 有多个目标时，较低目标优先获得有限买盘；同价按创建时间和 ID 稳定排序。
- 买入创建目标后必须立即复查当前同一盘口；若目标已达到，不得等到下一次行情事件才卖。
- 首次卖出后本轮停止继续买入并撤销该 Token 的活动买单。部分持仓继续等待目标卖出。
- 持仓完全卖出且市场仍开放、未正式结算、资格与完整轮次资金均满足时，下一次机会自动开始该 Token 的下一轮；资金不足时必须保持上一周期关闭状态，不提供手动“开始新一轮”按钮或 API。
- 正式结算过的 Condition 永久不能进入新一轮。

## 费用、资金与盈亏

- 使用市场公开动态费率与指数。`feesEnabled` 必须明确；启用费用时费率必须在 0–1、指数必须是 0–10 的安全整数，否则该市场失败关闭。买入费从所得份额扣除；卖出费从到账资金扣除；已实现和未实现盈亏均按净额计算。
- 总资金 = 可用现金 + 仍保留的现金 + 所有正数量当前持仓的可实现估值。
- 持仓估值优先使用当前完整盘口 Best Bid，并扣除预计卖出费用；明确没有 Bid 时可实现价值为 0，不能用成本价掩盖流动性缺失。
- 数据缺失可以在 UI 标记未知，但不能放宽实际成交门槛。

## 状态、配置与重置

- `开始TEST`只把当前账本切到 `RUNNING`并继续运行，不清空持仓、目标、资金、盈亏或审计。
- `暂停TEST`停止新买并撤销仍活动的旧买单未成交部分；目标卖出、结算和风险降低继续运行。
- 配置保存影响后续新买，不重写已有目标卖价。若旧活动买单因新配置失去资格，配置和撤单必须在同一 SQLite 事务内完成；失败时整体回滚。
- TEST 初始资金和每轮金额只在 TEST 配置中出现。初始资金默认 100U，每轮金额默认 1U；初始资金只能在 `PAUSED` 且没有任何交易历史时修改，有历史时必须先重置。
- 重置只能在 `PAUSED` 状态执行，并要求两次精确确认；它彻底清空 TEST 订单、成交、持仓、结算、配置、选择遗留数据、盘口消费和审计，恢复 100U、1U、50%、20%、1–30 天与 `PAUSED`。
- 多语句数据库迁移及版本登记必须在同一 SQLite 事务内完成；改变交易资格或执行模型的迁移必须把升级库强制置为 `PAUSED`。
- 周期账本验证必须交叉核对 fill 数值、订单成交量与费用汇总、由买入净份额减卖出份额反算的仓位、活动目标覆盖和资金守恒。失败时保留现场并暂停；除目标卖出减仓外冻结自动账本写入，验证恢复前禁止重新进入 `RUNNING`。

## 正式结算

- 只有市场 `closed=true`，且官方结算状态为 `resolved` 或 `settled` 时才处理。
- 只接受二元 `1/0` 或官方 `0.5/0.5` 结果；其他状态继续等待，不猜测结果。
- TEST 不调用钱包或链上赎回。获胜 Token 按正式结果模拟回收，失败 Token 归零；Condition ID 保证幂等。
- 身份冲突、重复结果不一致或账本异常时暂停并保留审计，不自动改写证据。

## UI

- 手机优先且桌面共用同一单列页面，至少支持 320px，不依赖横向表格。
- 左上角显示 `TEST / LIVE`；LIVE 锁定并只提示未开放。
- 默认内容仅保留配置入口、资金摘要、当前持仓和扫描市场；不显示最近活动、程序状态、服务器状态或验证细节。
- 配置包含 Polymarket 首页栏目、二元/三元、1–3¢ 买价、最低 Bid/Ask 比例、最大生命周期进度、总时长自由区间、TEST 总资金和每 Token 每轮金额。
- 资金区单行显示总资金、所有当前持仓按可执行净卖出价值汇总的实时价值，以及正数量持仓数；不再显示总盈亏、已实现和未实现卡片。
- 持仓显示可点击市场名、醒目的结果方向、平均买入价、当前 Best Bid、目标卖价、数量及市场全生命周期进度。
- 当前持仓默认显示前 20 项，其余折叠并可展开；折叠只影响页面，接口仍返回全部持仓。
- 扫描市场显示当前满足全部硬资格的可交易市场；行情重连时保留上次有效候选和价格并明确标记“重连中/不可交易”，避免误解为条件淘汰。每项显示可点击市场名、结果方向、当前或上次买/卖价、开始/结束时间和进度；默认 20 项，可展开；使用一个小按钮切换进度正序/倒序。
- 扫描状态必须区分事件遍历和盘口阶段，显示进度、监控数、可交易数，并保留逐规则淘汰计数供诊断；不能只显示笼统“扫描中”或把旧候选暂存误报为 0。
- 页面约每 500ms 拉取轻量面板数据，价格以两位小数美分显示；轮询不得覆盖未保存表单草稿。

## Linux 访问与验证顺序

- 服务器只部署 `TEST + LIVE_DISABLED`。Docker 应用端口只绑定 `127.0.0.1:3000`；公网只开放 Nginx 80/443，使用证书匹配的 HTTPS 主机名和登录认证。
- 登录凭据、Nginx密码哈希、`.env`、SQLite、备份和日志不得进入 Git。Basic Authentication 只适用于单用户 TEST，未来 LIVE 必须重新设计身份、会话、CSRF和审计。
- 部署顺序固定为：最终 UI 和执行闭环 → 本地验证 → GitHub `main` → 备份服务器数据/配置 → 部署同一 SHA → 短时冒烟 → 停止等待用户制定正式长期验证计划。
- 短时冒烟只验证接线、迁移、HTTPS、认证、状态、SQLite 和重启，不计入正式长期验证。
- 停止服务必须先中止在途扫描并关闭自动/行情后台循环；即使有大集合订阅和页面轮询，也应在进程截止时间内正常退出，不能靠延长超时掩盖平方级热路径。
- 到达正式长期验证阶段必须停止；运行时长、故障场景、资源门槛和通过标准由用户先制定。
