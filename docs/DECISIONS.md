# 已确认决策

本文件记录当前有效规则。历史方案、旧交接记录或代码注释与本文件冲突时，以 GitHub `main` 上的本文件为准。

## 安全与阶段边界

- 当前公开模式名为 `TEST`，初始状态为 `PAUSED`；内部 SQLite 表名和审计事件中的 `paper`/`PAPER`属于兼容实现，不是可启用的第二种模式。
- `LIVE` 执行器必须失败关闭。纸面闭环和用户制定的正式长期验证全部完成前，不接钱包、不签名、不发送真实订单、不执行链上写操作。
- TEST 与未来 LIVE 共用市场发现、资格判断、排序、买卖意图、目标价、费用和 FAK 计算；执行结果由适配器隔离。当前只实现 `TestExecutor`，未来 LIVE 仍需单独实现鉴权、下单、撤单、对账、恢复和安全门。
- 自动测试、短时冒烟、部署成功或用户点击 LIVE 都不构成实盘授权。

## 市场遍历与资格

- 用户要求遍历 Polymarket 全部符合条件的市场。扫描必须遍历官方开放事件的全部分页，不设置事件、市场或 Token 数量上限。
- 开放事件按页流式处理，不在内存中保留完整嵌套事件图。先应用不依赖盘口的结果数、类别、总时长、生命周期进度和体育开赛规则，再只为这部分 Token 获取订单簿；盘口请求可以有界并发和分片，但不得用隐藏数量上限截断。
- 不使用事件级开始/结束日期窗口预先截断，因为事件和其具体市场的时间可能不同；精确规则在每个具体市场上执行。
- 事件必须明确 `active=true`、`closed=false`、`archived=false`。具体市场也必须明确 active、未 closed/archived、`acceptingOrders=true`、`enableOrderBook=true`，并具有 Condition ID；缺失布尔状态不得推定为开放。
- 具体市场总时长定义为 `endsAt - openedAt`。优先读取市场自身 `state.startDate/endDate`，缺失时才回退到所属事件时间。
- 总时长最短值和最长值都由用户按完整天数自由设置，各自范围为 1–365 天，且最短值不得超过最长值；默认代表 `1 天 <= 总时长 <= 30 天`。例如设置 7–30 天时，只接受总时长不少于 7 天且不超过 30 天的市场。
- “剩余时间”不参与总时长筛选。市场仍须已经开始且尚未结束。
- 生命周期进度是硬资格门槛，配置范围 1% 至 100%，默认 `<=20%`；超过阈值立即从扫描清单和新买入中排除。排序仍可在合格市场内按进度正序或倒序。
- 体育市场在比赛开始后立即失去新买资格，未完成的旧买单撤销；已有持仓仍可卖出或等待结算。该规则必须进入统一资格函数，不能只在执行器临时拦截。
- 标准结构统一支持任意安全整数 `resultCount >= 2`。单 Market Event 固定视为二元；标准 Negative Risk Multi-Market Event 以完整 `event.markets.length` 作为结果数，允许任意 N；`negRiskAugmented=true` 继续排除。用户配置只有 `BINARY`（2）、`TERNARY`（3）、`MULTI`（4+）三类，不枚举 4、5、6 等结果数。旧库与重置默认保留二元/三元开启、多元关闭。
- 类别选择只显示 Polymarket 首页顶栏当前栏目，按官方 Tag ID 动态同步并默认全选；首页栏目变化后下一轮同步自动更新，一个市场可匹配多个 Tag。无官方标签的市场只在“全选”下参与，不制造 `OTHER` 等伪官方 ID。
- 非全选时，保存的栏目 ID 必须与本轮同步到的首页栏目取交集；已经退出首页导航的旧 ID 不得继续进入盘口请求或自动执行。栏目同步暂时失败时使用既有受控回退，不阻塞完整市场遍历。
- 不设历史成交量硬门槛。是否能够交易由当前可执行订单簿深度和最小下单量决定。

## 候选与价格

- 所有同时满足结构条件和当前“无盘口静态条件”的 Token 都进入实时盘口监控，包括当前价格高于上限或暂时无盘口的 Token；这样价格进入范围时可立即成为候选。每个 Token 必须携带 event/market/condition/token/direction/resultCount 完整身份；`resultCount` 不随部分子 Market 关闭而缩小。修改市场类型、类别、总时长或生命周期进度后必须立即重扫以更新监控池。
- 候选集合变化时在同一公开 WebSocket 上增量订阅或退订，并对大集合分片发送；不得为了普通扫描差异重建整条连接。真实断线时最后有效报价可以继续展示，但必须标记为重连/未就绪且禁止新买，直到该 Token 收到新的完整盘口。大集合的报价更新必须按 Token 索引定位，完整快照按尚未收到 Book 的 Token 集合判断，不能对每条行情重新遍历全部候选或订阅。
- 当前可买候选必须具有完整新鲜盘口和有效 tick；Best Ask 必须位于用户配置的最低/最高买价闭区间内；必须存在有效 Best Bid，且 `Best Bid / Best Ask` 不低于用户比例（1%–100%，默认 50%）；本轮金额按 Best Ask 计算后还须达到平台最小下单量。
- REST 或 WebSocket 盘口中的价格必须严格位于 0 与 1U 之间并可安全转换为整数微单位；REST 盘口还必须同时匹配 Token、Condition ID 和 neg-risk 身份，否则只保留监控对象并标记盘口未就绪。
- 最低与最高买价均可按 `0.1¢` 输入，范围为 `0.1¢–99¢`，且最低值不得超过最高值；默认买价范围为 `0.1¢–99¢`，不能以 `Best Ask > 0` 替代明确边界。
- 扫描结果不提供逐 Token 勾选。所有同时符合类别、结果数量、价格、买卖盘比例、生命周期进度、总时长和盘口条件的候选都自动参与 TEST。
- CandidateService 必须同时维护 `tokenId -> candidate`、`tokenId -> eventId` 和 `eventId -> siblings` 索引。Token 报价变化只重算所属 Event；定时全量校正可以遍历全部 Event，但实时路径不得遍历全候选。Event 已锁定后，兄弟 Token 普通报价变化不重新仲裁。
- 定时全量 Event 校正必须按有界时间片向 HTTP、行情和暂停请求让出事件循环；每次让出后若策略已不再 `RUNNING`，不得继续新买。自动化状态缓存只保留展示和重算所需的 Event 状态、Winner、Token 身份和版本摘要，不得为每个 Event 长期持有完整 Book、FAK Preview 或买入 Intent。
- 不同 Event 之间先按当前可交易状态分组：`READY` Event 固定排在待定 Event 前面；每组内部再按生命周期进度正序或倒序处理，默认正序。排序只影响跨 Event 顺序和展示，不放宽进度硬门槛。

## Event 完整性、FAK Preview 与仲裁

- 未锁定 Event 开启新周期前，全部静态合格兄弟 Token 都必须有新鲜完整 Book。已收到完整 Book 但没有有效 Bid/Ask 属于完整数据，只淘汰该 Token；未收到完整 Book、重连或未知状态会阻断整个 Event 开仓。Event 锁定后只要求 active Token 满足继续执行所需的数据，兄弟断线不妨碍退出。
- Event Arbitration 只比较通过全部 Token 硬资格且 FAK Preview 有实际成交量的机会。最高买价、Bid/Ask、生命周期、时间、体育开赛、Condition 身份、tick、最小量、费用、资金和订单金额继续是硬门槛，排序不能挽救不合格 Token。
- 无副作用 FAK Preview 与真实 TEST FAK Buy 共用同一个纯规划核心；必须带入完整 Ask/Bid Book、最新配置、可用现金、Event 冻结预算、费用、最小量、tick、book version 和该版本已持久化消费深度，返回逐 Fill 价格/数量/净份额/目标、总花费及可成交比例。Preview 不写订单、fill、position、资金或盘口消费。
- 每个 Preview 的 `Terminal Target` 是预计实际 Fill 目标卖价中的最高值。Exit Bid Coverage 必须按真实 SELL 的 target 顺序调用同一 `planFakSell()`，让所有 target 顺序消费同一份 mutable Bid Book；不同 target 不得重复使用同一档深度，覆盖量最多为 Preview 净持仓。Event 内确定性排序依次为：`Best Bid / Terminal Target` 退出就绪度；该共享深度语义下目标价及以上可退出数量对预计净持仓的覆盖；`previewSpent / cycleBudget`；`Best Bid / Best Ask`；买卖均扣费后的目标净收益率；生命周期 ASC/DESC；`marketId -> direction -> tokenId`。不使用人工加权总分，`NO_FILL` 不可成为 Winner。
- Winner 只是当前快照结果。执行前必须带配置版本、Event 状态、参与 Token 的盘口 revision/version 再次完整评估；状态变化时丢弃旧结果并按最新状态重仲裁，不能直接退回旧第二名。

## TEST 买入

- TEST 和未来 LIVE 都以实时可成交 Best Ask 为触发条件，不使用等待成交的 Maker 队列模型。
- 买入采用 FAK：在价格上限内从最低 Ask 向上逐档吃单；允许部分成交，未成交余量立即取消。
- FAK 买单按现金上限定义：现金完整使用时订单记为 `FILLED`，其原始份额和已成交份额都等于实际总成交份额；因深度不足只成交部分时订单记为 `CANCELLED`，不得用首档价格估算份额破坏账本不变量。
- 已消耗盘口深度按 BID/ASK 单侧完整盘口状态的稳定版本持久化。重复增量、等价快照、断线重连或进程重启都不得重新释放同一深度；只有该侧实际盘口状态改变后才形成新版本。
- 每个 Event 每轮使用一个现金上限，默认 1U；总 TEST 资金默认 100U。首笔实际 Fill 时把当前金额冻结到 Event Lock 的 `cycle_budget_micros`，配置在周期中增大不能扩大旧周期；新配置只在下一周期生效。已有部分周期只能把剩余额度继续用于同一 active Token，累计 spend 不得超过冻结上限。
- 行情、筛选或订单簿不完整时不推定成交。保存配置后，自动入口和诊断用手动 API 都必须立即复核当前配置。
- Event 第一次非零实际 Fill、`paper_event_locks`、BUY order、fills、position、target sells、资金和盘口消费必须在同一个 SQLite 事务提交；事务内重新规划并校验 Event 身份、锁、冻结预算、资金和可用深度。`NO_FILL` 或任一步失败不得留下锁或部分账本。
- 正常锁唯一表达 `eventId -> activeTokenId` 及其 market/condition 身份和冻结预算，不重复保存可从订单/Fill/Position 推导的 spent/PnL。锁定 A 后 B/C/D 禁止买入；A 只有在尚未卖出、仍满足最新新买资格且有剩余额度时可以继续累计。

## 目标卖出与循环

- 每个实际买入填充都立即创建目标卖单。用户可配置加价参数 `A` 和倍数参数 `B`，目标为 `min(99¢, 按该市场 tick 向上取整[max(买价 + A, 买价 × B)])`；默认仍为 `A=1¢`、`B=1.5`。配置只作用于后续新 Fill，已有目标卖单不追溯改写。
- Best Bid 达到或高于目标价时立即按 FAK 卖出，从最高可成交 Bid 向下消耗；允许部分成交，剩余数量继续等待同一目标，不主动降价，不设止损。
- 同一 Token 有多个目标时，较低目标优先获得有限买盘；同价按创建时间和 ID 稳定排序。
- 单个目标剩余份额低于市场最小下单量时，按上述稳定顺序累积同一 Token 的后续目标，达到最小量后合成一笔 FAK SELL；批次限价取所含目标中的最高价，成交再按稳定顺序分配回原目标。Preview/Arbitration 与真实 SELL 必须共用该批次规划及 mutable Bid 深度消费，每条持久化 Fill 的到账金额和费用都按自身价格与份额计算，保证可从账本证据精确重建。
- 买入创建目标后必须立即复查当前同一盘口；若目标已达到，不得等到下一次行情事件才卖。
- active Token 首次实际卖出后整个 Event 进入可从 `first_sell_at` 推导的退出阶段：active Token 和所有兄弟 Token 都不得继续买入，部分持仓继续等待目标卖出或正式结算。
- active Token 持仓为 0 且不再有任何活动卖单时，在造成最终清仓的同一 SQLite 事务释放 Event Lock。若 Event 仍有合法开放 Market，下一次机会重新仲裁；下一轮 Winner 可以是原 Token 或任意兄弟 Token。不提供手动“开始新一轮”按钮或 API。
- 正式结算过的 Condition 永久不能进入新一轮。

## 费用、资金与盈亏

- 使用市场公开动态费率与指数。`feesEnabled` 必须明确；启用费用时费率必须在 0–1、指数必须是 0–10 的安全整数，否则该市场失败关闭。买入费从所得份额扣除；卖出费从到账资金扣除；已实现和未实现盈亏均按净额计算。
- 总资金 = 可用现金 + 仍保留的现金 + 所有正数量当前持仓的可实现估值。
- 持仓估值优先使用当前完整盘口 Best Bid，并扣除预计卖出费用；明确没有 Bid 时可实现价值为 0，不能用成本价掩盖流动性缺失。
- 数据缺失可以在 UI 标记未知，但不能放宽实际成交门槛。

## 状态、配置与重置

- `开始TEST`只把当前账本切到 `RUNNING`并继续运行，不清空持仓、目标、资金、盈亏或审计。
- `暂停TEST`停止新买并撤销仍活动的旧买单未成交部分；目标卖出、结算和风险降低继续运行。
- 配置保存影响后续新买与这些新 Fill 创建的目标卖价，不重写已有目标卖价。若旧活动买单因新配置失去资格，配置和撤单必须在同一 SQLite 事务内完成；失败时整体回滚。
- TEST 初始资金和每轮金额只在 TEST 配置中出现。初始资金默认 100U，每轮金额默认 1U；初始资金只能在 `PAUSED` 且没有任何交易历史时修改，有历史时必须先重置。
- 重置只能在 `PAUSED` 状态执行，并要求两次精确确认；它彻底清空 TEST Event Locks、订单、成交、持仓、结算、配置、选择遗留数据、盘口消费和审计，恢复二元/三元开启、多元关闭、100U、每 Event 每轮 1U、买价 `0.1¢–99¢`、目标参数 `+1¢ / ×1.5`、50%、20%、1–30 天与 `PAUSED`。
- 结算请求在外部等待期间可能与 TEST 重置并发；任何请求结果或错误在写账前都必须同时核对本次进程内不可复用的 TEST reset 代次，以及当前订单、仓位和结算目标。即使新 TEST 对同一 Event/Market/Condition 重新开仓，旧代次结果也不得结算新仓、重建 `paper_settlements`、暂停新基线或写入旧活动审计。
- 多语句数据库迁移及版本登记必须在同一 SQLite 事务内完成；改变交易资格或执行模型的迁移必须把升级库强制置为 `PAUSED`。
- 周期账本验证必须交叉核对 fill 数值、订单成交量与费用汇总、由买入净份额减卖出份额反算的仓位、活动目标覆盖和资金守恒。失败时保留现场并暂停；除目标卖出减仓外冻结自动账本写入，验证恢复前禁止重新进入 `RUNNING`。
- Event 级验证还必须核对正常同 Event 最多一个正仓、正仓必有匹配锁、锁身份和 metadata/position/target 一致、兄弟无新 BUY、首次 Sell 后无新 BUY、累计 spend 不超冻结预算、无僵尸锁、settled Condition 无活动账本。只有迁移生成的 `LEGACY_CONFLICT` 可暂时保留同 Event 多 Token 旧仓；它禁止新 BUY，全部旧仓退出后自动释放。

## Schema 15/16 迁移兼容

- Schema 15 将 `paper_market_metadata.result_count` 约束放宽为 `NULL` 或安全整数 `>=2`，为 preferences 增加 `multi_enabled`，并新增以 `event_id` 为主键的 `paper_event_locks` 及 Event 查询索引。迁移与 schema version 登记保持同一事务并强制策略为 `PAUSED`。
- Schema 16 为 preferences 增加最低买价、可配置目标加价和目标倍数，并把最高买价放宽至 `99¢`；迁移保留原最高买价和已有 SELL targets，新增最低价取 `0.1¢`、目标参数取原规则 `+1¢ / ×1.5`，同时强制 `PAUSED` 并取消仍活动的 BUY。
- 迁移保留既有 binary/ternary 选择并把 multi 设为关闭；所有仍活动的旧 BUY 安全取消并释放对应预留现金，已有仓位、降低风险的卖单、Fill 与盈亏证据不删除。
- 没有正仓的 Event 不建锁；只有一个正仓 Token 的 Event 建立 ACTIVE 旧仓锁，冻结预算取已投入的 cycle spend/cost，因此只允许退出、不扩大旧风险；两个及以上正仓 Token 的 Event 建立无 active Token 的 `LEGACY_CONFLICT`，不得任意选择 Winner 或合并历史仓位。

## 正式结算

- 只有市场 `closed=true`，且官方结算状态为 `resolved` 或 `settled` 时才处理。
- 只接受二元 `1/0` 或官方 `0.5/0.5` 结果；其他状态继续等待，不猜测结果。
- TEST 不调用钱包或链上赎回。获胜 Token 按正式结果模拟回收，失败 Token 归零；Condition ID 保证幂等。
- 具体 Condition 结算、仓位清理、活动订单处理和 Event Lock 释放必须原子完成。一个子 Market 结算只永久终止该 Condition，不把整个 Event 标成永久关闭；仍开放的兄弟 Market 可在解锁后的下一轮参与仲裁。
- 身份冲突、重复结果不一致或账本异常时暂停并保留审计，不自动改写证据。

## UI

- 手机优先且桌面共用同一单列页面，至少支持 320px，不依赖横向表格。
- 左上角显示 `TEST / LIVE`；LIVE 锁定并只提示未开放。
- 默认内容仅保留配置入口、资金摘要、当前持仓、交易记录和扫描市场；不显示程序状态、服务器状态或验证细节。交易记录位于当前持仓和扫描市场之间，默认折叠，点击整行展开或收起，并按时间倒序展示 TEST 账本中的开仓、加仓、部分平仓、已平仓和结算；同一订单同批次的多档 Fill 聚合为一条记录，批次以持久化成交源标识判断，不能用毫秒时间戳代替。
- 配置包含 Polymarket 首页栏目、二元/三元/多元（4+）、`0.1¢–99¢` 最低/最高买价、完整目标卖价公式及可配置 `A/B` 参数、最低 Bid/Ask 比例、最大生命周期进度、总时长自由区间、TEST 总资金和每 Event 每轮金额。
- 资金区单行显示总资金、已实现盈亏、未实现盈亏、所有当前持仓按可执行净卖出价值汇总的持仓价值，以及正数量持仓单数。
- 持仓显示 Event、active Token/Market/方向、平均买入价、当前 Best Bid、目标卖价、数量、冻结预算、已用金额、累计/退出/旧仓冲突状态及市场全生命周期进度。
- 当前持仓默认显示前 20 项，其余折叠并可展开；折叠只影响页面，接口仍返回全部持仓。
- 扫描主列表按 Event 聚合，不把多结果 Event 的兄弟 Token 铺成独立机会。每项显示 Event 标题、N 元类型、市场/Token 数、当前 Winner 的 Market/方向和买卖价、Event 状态、兄弟结果摘要及生命周期；行情重连时明确标记等待兄弟盘口。默认 20 个 Event，可展开；`READY` 可交易 Event 固定置顶，可交易组与待定组内部使用一个小按钮切换生命周期进度正序/倒序。
- 扫描状态必须区分事件遍历和盘口阶段，显示进度、监控数、可交易数，并保留逐规则淘汰计数供诊断；不能只显示笼统“扫描中”或把旧候选暂存误报为 0。
- 页面约每 500ms 拉取轻量面板数据，价格以两位小数美分显示；轮询不得覆盖未保存表单草稿。

## Linux 访问与验证顺序

- 服务器只部署 `TEST + LIVE_DISABLED`。Docker 应用端口只绑定 `127.0.0.1:3000`；公网只开放 Nginx 80/443，使用证书匹配的 HTTPS 主机名和登录认证。
- 登录凭据、Nginx密码哈希、`.env`、SQLite、备份和日志不得进入 Git。Basic Authentication 只适用于单用户 TEST，未来 LIVE 必须重新设计身份、会话、CSRF和审计。
- 部署顺序固定为：最终 UI 和执行闭环 → 本地验证 → GitHub `main` → 备份服务器数据/配置 → 部署同一 SHA → 短时冒烟 → 停止等待用户开始正式长期验证。
- 短时冒烟只验证接线、迁移、HTTPS、认证、状态、SQLite 和重启，不计入正式长期验证。
- 停止服务必须先中止在途扫描并关闭自动/行情后台循环；即使有大集合订阅和页面轮询，也应在进程截止时间内正常退出，不能靠延长超时掩盖平方级热路径。
- 正式长期验证采用用户确认的累计 72 小时：每 4 小时及配置变化形成独立片段，片段默认待决定，只有无硬失败且经用户明确确认的时长计入；有效采样率或墙钟采样覆盖率低于 99.5%，以及出现安全、SQLite、账本和关键服务失败的片段自动拒绝。达到 72 小时后仍须最终审计。
