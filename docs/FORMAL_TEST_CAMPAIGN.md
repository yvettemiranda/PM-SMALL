# 正式 TEST 累计 72 小时验证手册

本手册是 PM-SMALL 正式长期 TEST 的唯一执行口径。当前只部署管理工具，未经用户另行明确发出“开始”指令，不运行本任务，不调用 `/api/test/start`。

## 已确认规则

- 目标是用户确认计入的健康时长累计达到 72 小时，不要求一次连续跑满；
- 从任务开始时间起每 4 小时形成一个节点；交易配置发生变化时，在配置的 `updatedAt` 处额外切段；
- 每个完成片段默认都是“待决定”，不会自动计入；
- Codex 先读取服务器证据、向用户说明该段结果，再由用户明确选择“计入”或“排除”；不得根据沉默、历史选择或主观判断代替用户决定；
- 安全、LIVE、SQLite、账本、周期验证或核心运行服务硬失败，以及有效采样率或按 60 秒间隔计算的采样覆盖率低于 99.5% 的片段自动拒绝，不能由人工强行计入；
- 达到 72 小时只代表累计时长达标，仍需完成最终数据与证据审计，不能直接等同于 v0.5 正式验收通过。

最长墙钟时间默认 120 小时，用于容纳被排除片段和用户等待决定的时间。达到累计 72 小时、出现硬失败、收到停止命令或超过 120 小时时，管理工具都会请求并确认策略回到 `PAUSED`。

## 并行方式

业务程序只保留一套全市场扫描、行情流、TEST 自动买卖、结算和周期验证。独立监控容器只并行读取以下本机接口，不发起第二套市场扫描，因此不会人为放大 Polymarket 请求量、限流数或服务器资源：

- `GET /api/status?compact=true`
- `GET /api/test/validation`
- `GET /api/test/preferences`

采样间隔为 60 秒。完整原始样本写入 `observations.jsonl`；每段摘要同时保存进 `campaign.json` 和 `REPORT.md`。`server-context.json` 固定记录仓库提交、业务容器/镜像、监控镜像和基线备份，避免最终审计混淆实际受测版本。

## 每段报告内容

每个 4 小时或配置变化节点至少记录：

- 起止时间、片段时长、边界原因、配置快照与配置指纹；
- 有效样本率、墙钟采样覆盖率、告警样本、传输错误和不可重复计入的硬失败；
- 请求耗时、RSS、堆内存、候选数和扫描耗时峰值；
- 扫描重试、限流、临时错误及行情订阅完整率；
- WebSocket 异常断线/恢复计数的首末值；
- TEST 买入成交、卖出成交、自动买单、结算和周期验证计数的首末值。

原始样本保留更完整的资金、仓位、扫描、行情、仲裁、结算和账本字段，供最终审计使用。

## 一次性准备

服务器仓库必须是已验证的 GitHub `main`，业务程序必须为 `TEST + LIVE_DISABLED + PAUSED` 且即时账本验证通过。然后只构建独立监控镜像：

```bash
cd /home/ubuntu/pm-small
./scripts/formal-test-campaign.sh prepare
```

`prepare` 不启动 TEST、不重启业务容器，也不改变数据库。它使用当前 Git SHA 构建 `pm-small-formal-test:<12位SHA>`，并在结束前再次确认仍为 `PAUSED`。

## 将来正式开始

只有用户在新的消息中明确要求开始后，才执行：

```bash
cd /home/ubuntu/pm-small
./scripts/formal-test-campaign.sh start --confirm START-TEST-72H
```

该命令自动完成以下工作：

1. 确认 TEST、LIVE 禁用、策略 PAUSED、SQLite 和账本健康；
2. 停止业务容器，复制 `data/`、`.env`、`docker-compose.yml`，生成并复核 SHA-256 基线备份；
3. 恢复同一业务容器并再次确认安全 PAUSED；
4. 创建独立证据目录和单一监控容器；
5. 由带显式确认词的运行器调用一次 `/api/test/start`；
6. 验证任务和业务策略都安全进入 `RUNNING`。

监控容器崩溃或宿主机重启时不会续跑或重复调用开始接口；它发现已有任务后会先请求 `PAUSED` 并保留现场，等待人工审计。

正式开始时还应在当前 Codex 任务建立每 4 小时一次的提醒。提醒只唤醒 Codex 读取状态并向用户报告待决定片段，不自动执行“计入”。

## 平时查看

用户只需问 Codex“测试情况怎么样”。Codex 在服务器执行：

```bash
cd /home/ubuntu/pm-small
./scripts/formal-test-campaign.sh status
```

回复至少要区分：

- 当前是运行中、已暂停、失败还是累计时长已达标；
- 已确认计入 / 72 小时；
- 待用户决定的片段、时长和健康摘要；
- 已排除与硬失败拒绝时长；
- 当前 TEST/LIVE/策略安全状态；
- 本轮新增成交、异常、限流、断线恢复和资源峰值。

## 用户决定片段

Codex 必须先报结果，再取得用户对具体片段的明确答复。用户确认后执行其中一个命令：

```bash
./scripts/formal-test-campaign.sh include segment-0001
./scripts/formal-test-campaign.sh exclude segment-0001
```

`include` 只接受已完成且具备计入资格的片段；硬失败片段会被拒绝。决定以追加记录写入 `decisions.jsonl`，不会覆盖历史证据。配置改动不需要重启任务；下一次采样会按服务端精确更新时间切出新片段，之前片段继续单独等待决定。

## 停止

用户要求停止、硬失败或需要改变运行时代码时，执行：

```bash
./scripts/formal-test-campaign.sh stop
```

停止命令先写入控制证据，再反复请求并确认 `PAUSED`，最后停止监控容器。不得通过直接杀进程代替受控停止。若需要部署新代码，当前任务先停止并结案；新代码不得无证据地延续旧代码的累计时长。

## 最终审计

累计确认时长达到 72 小时后，必须保持 `PAUSED` 并完成：

1. 所有完成片段都有用户决定，硬失败片段均未计入；
2. `campaign.json`、`REPORT.md`、`decisions.jsonl`、`observations.jsonl` 与基线备份可对应；
3. 即时验证、SQLite `integrity_check`、资金守恒、订单、Fill、持仓、targets、Event Lock、结算和盘口消费一致；
4. 核对扫描完整轮次、真实限流/重试、WebSocket 容量/断线恢复、服务器资源和成交/结算样本；
5. 对最终数据库与证据生成 SHA-256，执行同库冷启动恢复并再次验证；
6. 单独给出“通过 / 有条件通过 / 不通过”结论和未覆盖项。

无论结果如何，钱包、签名、LIVE 下单和链上写入都不在本计划授权范围内。
